# Архитектура модуля Wi‑Fi ваучеров

## Решение для онлайн-пилота

Модуль разворачивается как один Docker Web Service на Render:

- FastAPI отдаёт интерфейс и версионированный API;
- LibreOffice внутри контейнера формирует PDF из PPTX-шаблонов;
- Supabase Postgres хранит пароли, статусы и историю генераций;
- GitHub является источником кода и запускает проверки перед автодеплоем.

Vercel сейчас не используется для генератора: LibreOffice является тяжёлой
системной зависимостью, а модуль относится к коммерческой работе отеля.
В дальнейшем Vercel подходит для общей панели, которая будет вызывать API
этого сервиса.

## Режимы работы

### Standalone

- один отель задаётся через `HOTEL_ID` и `HOTEL_NAME`;
- доступ защищён `ADMIN_USERNAME` / `ADMIN_PASSWORD`;
- интерфейс и API находятся на одном домене;
- локальная разработка может продолжаться на SQLite без Supabase.

### В составе общей панели

- общая панель получает отдельный frontend на Vercel или другой платформе;
- модуль сохраняет API `/api/v1`, PostgreSQL-схему и бизнес-правила;
- Basic Auth заменяется адаптером OIDC/JWT;
- `hotel_id` берётся только из проверенного server-side токена и прав
  пользователя, а не из произвольного заголовка браузера;
- endpoint `/api/v1/module-manifest` сообщает панели версию и возможности
  модуля.

## Контракт API

- `GET /api/v1/passwords` — доступный пул, поиск и пагинация;
- `POST /api/v1/passwords/import/preview` — проверка новой партии и дубликатов;
- `POST /api/v1/passwords/import` — идемпотентное добавление новых значений;
- `PATCH /api/v1/passwords/{id}` — ручная правка доступного значения;
- `POST /api/v1/passwords/issue` — атомарно скопировать и отметить выданными;
- `POST /api/v1/passwords/delete` — удалить выбранные доступные значения;
- `POST /api/v1/generations` — зарезервировать пароли и сформировать PDF;
- `GET /api/v1/generations` — история генераций;
- `GET /api/v1/module-manifest` — метаданные для общей панели;
- `GET /health` и `GET /ready` — liveness и проверка базы.

Старые URL сохранены как временные совместимые aliases, но новая панель должна
использовать только `/api/v1`.

## Модель данных и границы отеля

Таблицы находятся в закрытой схеме Postgres `wifi_voucher`, которая по
умолчанию не публикуется через Supabase Data API:

- `hotels`;
- `passwords`;
- `generations`.

Все рабочие запросы фильтруются по `hotel_id`. Уникальность пароля задаётся
парой `(hotel_id, password)`, поэтому один отель не видит данные другого.

Статусы: `available → reserved → used`. Ручная команда
«Скопировать и выдать» выполняет `available → used` в одной транзакции.
Повторный импорт такого значения блокируется уникальным ограничением.

## Устойчивость

- PostgreSQL-резервирование использует `FOR UPDATE SKIP LOCKED`;
- незавершённые резервы имеют lease и освобождаются после TTL;
- ошибка LibreOffice возвращает пароли в доступные;
- Render может пересоздать контейнер без потери данных, потому что состояние
  находится в Supabase;
- локальная SQLite-база остаётся аварийной переносимой копией.

## Ограничения бесплатного пилота

- Render Free засыпает после периода без входящих запросов; первый запуск может
  занять около минуты;
- локальная файловая система Render эфемерна;
- Supabase Free может приостановить малоактивный проект;
- бесплатный Supabase не предоставляет автоматические резервные копии.

Для ежедневной эксплуатации без холодных стартов потребуется платный compute
хотя бы на уровне backend. До этого нужен регулярный защищённый `pg_dump`.

## Секреты

В Git нельзя добавлять:

- `DATABASE_URL`;
- `ADMIN_PASSWORD`;
- Supabase database password;
- выгрузки или backups с Wi‑Fi паролями.

Render Blueprint запрашивает эти значения через `sync: false`.
